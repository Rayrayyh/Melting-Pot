# Rate limiting and endpoint closure live in the database

Decision: abuse protection is enforced in Postgres, not in the app or the edge, because the database is the only door every client goes through (browser, direct REST, a script). Migrations 0014 (rate limits) and 0015 (grant revocations), later refined by 0017 (attachment read scope) and 0018 (open-correction count).

Rate limiting (0014): a `rate_limits(action, key)` table plus `consume_rate_limit(action, key, max, window)` gives every privileged RPC a fixed-window limit, keyed per user for authenticated actions and per IP for anonymous ones (`client_ip()` off X-Forwarded-For). Client-writable tables (contributions, revision_proposals, proposal_events, attachments, sections) carry per-user insert limits via a `rate_limit_insert()` trigger. `dev_seed`/`dev_reseed` set `app.bypass_rate_limit` transaction-locally for bulk inserts.

Sizing rule: anonymous per-IP limits must clear a whole class arriving from behind one school NAT at once (tens of requests), while still blocking abuse (thousands). Hence registration 200/hour, code lookup 400/10 minutes, join 120/hour per user. The first cut (20/hour registration) was wrong — it would have blocked a classroom — and is the reason these numbers are generous. client_ip() off a client-supplied header is best-effort; the per-user limits are the real enforcement, and per-IP is defense in depth for the pre-auth surface only.

Endpoint closure (0015): the anonymous role has no table access at all — its whole surface is `lookup_pot_by_code`, `register_student`, and GoTrue sign-in. The authenticated role keeps only the write verbs the app actually uses (audited from every `.from().insert/update/delete` call): contributions insert+update, attachments insert+delete, memberships delete + last_seen_note_id column update, pots update+delete, sections insert/update/delete, proposal_events insert, revision_proposals insert. Everything else — shared_notes, note_versions, all decision/version writes — is RPC-only. Revoking a verb removes it from the PostgREST surface entirely, so RLS is no longer the only thing standing between a client and an unused endpoint.

Consequence: this was applied to the single production project (the owner directed one database, no separate dev project). The dev seed functions are restored ad hoc for a test run and dropped + wiped before finishing, same as the pre-launch cleanup in decision 008. A couple of revoked verbs (contributions delete, profiles update) orphan RLS policies that had no UI anyway; restoring either is a one-line grant if a discard-draft or edit-name feature is added later.
